## Why it's non-cosmetic

Discovery is *how the outbound payment leg finds counterparties*. Today `query_agent`
resolves peers from a static env map (`BASE_SEPOLIA_AGENTS`). We replace that with ENS
text-record resolution + ERC-8004 verification, so **agents discover and pay each other
through ENS alone** — pull ENS and agent-to-agent commerce stops working. That's the bar.

## Exact spec (fetched from docs.ens.domains; both status: draft)

### ENSIP-26 — Agent Text Records (2 keys, extend ENSIP-5 `text(node,key)`)
1. **`agent-context`** — free text/markdown/JSON. The agent's "index.html": describes it,
   may reference its registration + endpoint records. Resolution loads this FIRST.
2. **`agent-endpoint[<protocol>]`** — value MUST be a valid URL. Protocols:
   - `agent-endpoint[mcp]` — MCP endpoint
   - `agent-endpoint[a2a]` — A2A endpoint
   - `agent-endpoint[web]` — human web URL
   - `agent-endpoint[x402]` — **spec-legal extension** → our x402 paywall URL.

### ENSIP-25 — Agent Registry Name Verification (1 parameterized key)
- Key: **`agent-registration[<registry>][<agentId>]`**, value SHOULD be `"1"` (clients
  depend only on non-emptiness).
  - `<registry>` = **ERC-7930 interoperable address** of the registry contract.
  - `<agentId>` = registry's agent id string; MUST NOT contain `[` or `]`.
- **Verification flow (mandated):** registry entry *claims* an ENS name → construct the
  key → resolve `text()` on the claimed name → **non-empty = verified; empty/missing =
  MUST fail**. (Registry-to-ENS direction; the text record is the name owner attesting back.)
- Base mainnet registry param (derive via ERC-7930; chainRef 8453=`0x2105`):
  `agent-registration[0x00010000022105148004a169fb4a3325136eb29fa0ceb6d2e539a432][<agentId>]="1"`.
  **Verify the ERC-7930 encoding with a lib before demo** (don't trust this by hand).
- Security: attestations go stale on name transfer — clients SHOULD check ownership.

## ERC-8004 — VERIFIED interface & deep usage (from EIP-8004 + on-chain checks)

> Interface pulled from eips.ethereum.org/EIPS/eip-8004. Addresses verified to have

### IdentityRegistry (ERC-721; agentId = incremental tokenId)
- `register(string agentURI, MetadataEntry[] metadata) → uint256 agentId` (also `register(agentURI)` / `register()`)
- `setAgentURI(uint256 agentId, string newURI)` · `setMetadata(agentId, key, bytes)` · `getMetadata(agentId, key)`
- **`setAgentWallet(agentId, newWallet, deadline, signature)`** / `getAgentWallet(agentId)` — cryptographically binds the agent identity to its payment wallet. **Use this to bind each Slopstock agent's wallet to its 8004 id.**
- events: `Registered(agentId, agentURI, owner)`, `URIUpdated`, `MetadataSet`.

### Agent card / registration file schema (what agentURI resolves to)
```json
{ "type":"https://eips.ethereum.org/EIPS/eip-8004#registration-v1",
  "name":"…","description":"… (may include pricing)","image":"…",
  "services":[{"name":"x402|MCP|A2A|ENS|web","endpoint":"https://…","skills":[]}],
  "x402Support": true,
  "active": true,
  "registrations":[{"agentId":1,"agentRegistry":"eip155:8453:0x8004A169…a432"}],
  "supportedTrust":["reputation","crypto-economic","tee-attestation"] }
```
Note `x402Support:true` and `supportedTrust:["tee-attestation"]` map to *exactly* our
capabilities (x402 paywall + sealed TEE inference). The card is where we advertise both.
Store it on **Walrus** and point `agentURI` at the aggregator URL → ties the ENS, Walrus,
and 8004 work together.

### ReputationRegistry — the valuation/credit layer
- `giveFeedback(agentId, int128 value, uint8 valueDecimals, string tag1, string tag2, string endpoint, string feedbackURI, bytes32 feedbackHash)`
- `getSummary(agentId, address[] clients, tag1, tag2) → (count, summaryValue, valueDecimals)` — aggregate score.
- `readAllFeedback(...)`, `getClients(agentId)`, `revokeFeedback`, `appendResponse(...)`.

### ValidationRegistry — proof-of-work-quality (our TEE receipts fit here)
- `validationRequest(address validator, agentId, string requestURI, bytes32 requestHash)`
- `validationResponse(bytes32 requestHash, uint8 response /*0–100*/, responseURI, responseHash, tag)`
- `getSummary(agentId, validators[], tag) → (count, averageResponse)`

### The deep-usage ladder (what we actually build)
- **L0 Register** — `register()` each agent on Base; publish card to Walrus; `setAgentURI`. Auto-listed on 8004scan/agentscan. (Also the ENSIP-25 prerequisite.)
- **L1 Bind** — `setAgentWallet` (id↔wallet) + ENSIP-25 record (id↔ENS name) + our iNFT/vault. Reputation now accrues to an asset with a cap table.
- **L2 Reputation-weighted payments (TARGET, demo-worthy)** — `query_agent` calls `getSummary` to rank payable peers by reputation BEFORE paying; after a job, calls `giveFeedback`. The standard's trustless loop, live: discover → assess trust → pay (x402) → attest.
- **L3 Validation via TEE (stretch)** — submit our TEE-attested receipt as a `validationResponse` (0–100), making "the work was real" verifiable, not claimed.
- **L4 (vision, not weekend)** — identity + cashflows + reputation + validation + Walrus memory lineage = a complete agent **balance sheet + credit report**. The investable-agent diligence package nobody else has assembled.
