# 05 — x402 v2 (real spec, both directions)

> **USER-MANDATED (2026-06-13):** "we shall fix it and have the real x402 v2 spec most
> definitely, no way of having it any other way." No homegrown challenge+txHash.

## Why (the user is right)

The homegrown flow (custom challenge → raw `USDC.transfer` → submit txHash) only works
because *our own client* speaks our private dialect — the "agentic commerce is real" thesis
dies if our agents can only transact with each other. Real x402 v2 collapses **inbound,
outbound, and discovery** onto one standard:
- Any standard x402 client can discover + pay our agents with zero coordination.
- Outbound to Exa/CoinGecko *requires* v2 as a client anyway → one protocol end-to-end.
- Settling via CDP facilitator **auto-lists us on the x402 Bazaar** (inbound discovery free).

## What changes

| | Homegrown (now) | x402 v2 (target) |
|---|---|---|
| Challenge | custom JSON | HTTP 402 + `x402Version:2`, `accepts[]` (scheme `exact`, network `eip155:8453`, amount, payTo, asset, maxTimeoutSeconds) |
| Payment | raw `USDC.transfer`, payer pays gas | EIP-3009 `transferWithAuthorization`, signed authorization in `X-PAYMENT` header, gasless for payer |
| Settle | read Transfer logs by txHash | facilitator verifies + submits |
| Libs | none | **`@x402/*` v2 scope** (see below) |

### VERIFIED v2 facts (don't repeat the v1 mistake)
- The unscoped `x402` / `x402-fetch` / `@coinbase/x402` npm packages are the **frozen v1 line** (`x402Version: 1`, legacy named networks "base"/"base-sepolia"). DO NOT use them.
- **v2 lives under the `@x402/*` scope @ 2.15.0:** `@x402/core` (schemas, client `x402Client`, server `x402HTTPResourceServer`, `HTTPFacilitatorClient`), `@x402/evm` (exact-scheme EVM), `@x402/fetch` (client), `@x402/hono`/`@x402/express`/`@x402/next` (server adapters), `@x402/mcp` (x402 for MCP servers — relevant, we expose one). Installed in `apps/operator`.
- **`x402Version = 2`** (from `@x402/core`). Networks are **CAIP-2** (`eip155:8453`, `eip155:84532`) via `NetworkSchemaV2` — NOT named. `network.ts` now carries CAIP.
- v2 `PaymentRequirements` required fields (from `PaymentRequirementsV2Schema`): `scheme, network, amount, asset, payTo, maxTimeoutSeconds` (note **`amount`**, not v1's `maxAmountRequired`). `resource`/`description`/`extra` optional.
- Helpers: `parsePrice("$0.10","eip155:8453") → {amount, asset}`; `safeBase64Encode/Decode` for the `X-PAYMENT` header; `validatePaymentRequirements`, `isPaymentRequirementsV2` guards.
- DONE so far (TDD, green): `buildAgentPaymentRequirements()` validates against `PaymentRequirementsV2Schema`; network config on CAIP.

Touch points: `apps/operator/src/http/server.ts` (402 issue + verify), `query_agent`
(client payment), receipt recording. Server uses `@x402/core` facilitator client +
hand-built requirements (fits our custom Bun.serve + dynamic per-token price/vault),
rather than the full `x402HTTPResourceServer` middleware.

## The settlement decision: CDP facilitator (primary)

   self-validate on-chain). No Bazaar auto-listing. Use if CDP setup snags at venue.
